# Local defence verification — reviewed 12 September 2026

**Result: the tested WAF rules block these request probes; operator-approved IP blocking works. Autonomous forecasting-to-blocking is not implemented/enabled by this test.**

## Scope and isolation

The harness starts a temporary copy of the shipped Node proxy bound to loopback, with a local inert HTTP backend. The backend records whether each tagged request actually arrives, and never evaluates SQL, templates, XML entities, shell commands or outbound fetch parameters. No public host was attacked. This is a bounded request-filtering and policy-integration check, not successful exploitation of a vulnerable application or a full penetration test.

Two profiles ran: shipped counter memory, then a fresh counter-memory profile created only in the temporary copy. The original project memory was unchanged. Each payload used a distinct simulated client IP via an explicitly trusted loopback forwarder. This topology tests proxy enforcement, not network-layer source spoofing resistance. Online signature learning remains enabled during each run, so the cases are not statistically independent.

## Results

| Check | Shipped memory | Fresh counter memory |
|---|---:|---:|
| Attack probes denied and absent from backend log | 12/12 | 12/12 |
| Benign requests forwarded | 5/5 | 5/5 |
| Unauthenticated management request | 401 | 401 |
| Retired predictive-lockdown route with operator token | 410 | 410 |
| Operator policy prevents backend access | 403, yes | 403, yes |
| Revocation restores backend access | 200, yes | 200, yes |

Attack probes: SQL tautology, UNION SELECT, script XSS, SVG XSS, path traversal, shell metacharacters, template expression, JSON NoSQL operators, form-encoded SQL injection, XML external entity syntax, loopback SSRF parameter, double-encoded SQL injection. All received HTTP 403 in both profiles.

Benign probes: homepage, ordinary search, an apostrophe in a name, ordinary use of “union”, and a normal JSON note. Five benign cases cannot establish a production false-positive rate.

For twelve repeated incorrect local login requests, shipped-memory statuses were 401, 401, then 403 for requests 3–9, and 429 for requests 10–12. Fresh-memory statuses were 401 for requests 1–7, 403 for requests 8–9, then 429 for requests 10–12. The backend intentionally returns 401; a backend 401 is not counted as a WAF block. Multiple existing defence mechanisms contribute to the sequence.

## Forecasting versus enforcement

A deliberately selected high-risk **previously stored service-graph snapshot** produced a peak malicious-flow forecast of approximately 0.9181 and `alert=true`. It returned `automatic_containment=false`. An ordinary local request still reached the backend after the forecast (HTTP 200).

An explicit operator policy for the chosen lab client IP then prevented backend access (HTTP 403), and revoking that policy restored access (HTTP 200).

The stored snapshot is not telemetry generated by the live request probes. Service graphs do not attribute that forecast to the chosen lab client IP. Therefore this is **not** an end-to-end demonstration of predicting these attacks and automatically preventing them. The result establishes that reactive request filtering and the operator enforcement mechanism work for the cases tested; it does not establish proactive defence.

## Remaining findings

- Shipped historical sensitivity counters are unusually large (one SQL category contributed +7400 in reported reasons). The fresh-memory run addresses dependence on that prior state for these probes only. Those counters are not proof of confirmed breaches.
- Some legacy reason strings claim “zero-day” interception. These are labels generated by legacy heuristics, not verified zero-day evidence.
- No volumetric DDoS, parser desynchronization, TLS deployment, multi-tenant boundary, persistence/privilege escalation, or exhaustive bypass campaign was evaluated here.
- The earlier host-model unseen-family result (40/40 labelled negative examples falsely alerted) is unchanged by successful WAF filtering. The two evaluations measure different components.
- Automatic containment remains disabled; this task did not activate it or change defence rules.

## Reproduce

Extract this bundle into the KrishnaDefence project root, preserving `security_validation/`. Python dependencies used by Garuda v3 and Node.js must already be installed.

```bash
PYTHONPATH=. python3 security_validation/local_attack_test.py
GARUDA_LAB_CLEAN_MEMORY=1 PYTHONPATH=. python3 security_validation/local_attack_test.py
```

Raw evidence is in `local_attack_results.json` and `clean_memory_results.json`. Per-request backend-arrival flags, HTTP status, reasons, and policy transitions are retained. The harness creates and terminates its local services and discards its temporary state.
